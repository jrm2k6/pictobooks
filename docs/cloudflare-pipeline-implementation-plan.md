# Cloudflare Pipeline Implementation Plan

Last updated: 2026-11-10

This is the base plan for coding agents implementing the production Pictobook pipeline. It applies [ADR 0001](./adr/0001-bounded-durable-pipeline-jobs.md) and [ADR 0002](./adr/0002-cloudflare-production-platform.md) without changing the validated generation, QA, or repair policy.

## Target architecture

```text
Browser / review dashboard
          |
          v
Authenticated Worker API
  |       |          |
  |       |          +----> R2: private binary and JSON artifacts
  |       +---------------> D1: product and workflow state
  +-----------------------> Workflow: one durable Book Run
                                  |
                                  +--> provider API calls
                                  |
                                  +--> Node image worker in Container
                                         | read inputs from R2
                                         | write outputs to R2
                                         + return metadata only
```

Queues are deliberately absent from the baseline. Workflows already provide durable multi-step orchestration. Introduce a Queue only after a load test demonstrates a concrete need for burst buffering or separately scaled page consumers. If added, its consumer must tolerate duplicate delivery.

## Component responsibilities

| Component        | Owns                                                                                                   | Must not own                                             |
| ---------------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| Worker API       | authentication, authorization, upload initiation, review actions, status reads, signed artifact access | image processing, long synchronous Book Runs             |
| D1               | books, photos, pages, workflow state, attempts, budgets, approvals, audit events, artifact metadata    | image bytes, large model responses                       |
| R2               | Source Photos, normalized inputs, Candidates, QA JSON, style assets, final output                      | mutable state inferred only from object listing          |
| Workflow         | durable orchestration, bounded transitions, retry scheduling, terminalization                          | large payloads, unbounded agent decisions                |
| Node Container   | `sharp` normalization, cleanup, deterministic Print QA, other native/CPU processing                    | durable state, retry policy, provider-attempt allocation |
| Provider adapter | Nano Banana/Gemini request and response translation                                                    | workflow policy, direct database state transitions       |
| Dashboard        | review and approval commands, status presentation                                                      | deciding server-side authorization or readiness          |

## Durable identifiers and object layout

Use opaque stable IDs. IDs are lowercase UUIDs or another documented collision-resistant format; filenames supplied by customers are metadata, never keys.

```text
books/{book_id}/runs/{run_id}/photos/{photo_id}/source/{source_revision}
books/{book_id}/runs/{run_id}/photos/{photo_id}/normalized/{normalization_revision}.png
books/{book_id}/runs/{run_id}/pages/{page_id}/briefs/{brief_revision}.json
books/{book_id}/runs/{run_id}/pages/{page_id}/candidates/{candidate_id}/raw.png
books/{book_id}/runs/{run_id}/pages/{page_id}/candidates/{candidate_id}/clean.png
books/{book_id}/runs/{run_id}/pages/{page_id}/candidates/{candidate_id}/print-qa.json
books/{book_id}/runs/{run_id}/pages/{page_id}/candidates/{candidate_id}/style-qa.json
books/{book_id}/runs/{run_id}/exports/{export_revision}/book.pdf
style-packs/{style_pack_version}/style-bible.md
style-packs/{style_pack_version}/canonical/{canonical_reference_id}.png
```

Every artifact record includes:

- `artifact_id`, `object_key`, `artifact_kind`, and `schema_version`;
- `sha256`, byte size, MIME type, and creation time;
- its producing operation and relevant source artifact IDs;
- provider/model metadata when generated by a model;
- retention class and deletion status.

Object writes use a new immutable key. Updating an artifact means creating a new revision and changing a D1 reference transactionally. Never overwrite an approved Candidate or Canonical Reference in place.

## Minimum D1 model

The first schema should include:

- `books` and `book_runs`;
- `photos` and `pages`;
- `candidates`;
- `artifacts` and `artifact_relations`;
- `operations` for idempotency claims and outcomes;
- `provider_attempts` for request IDs, status, timing, token/credit cost, and failure classification;
- `qa_results` for Print QA and Style QA summaries;
- `repair_rounds`;
- `reviews` and `canonical_references`;
- `audit_events`.

The database is the index. Normal API requests must not discover application state by listing an R2 bucket.

## State-machine invariants

Agents must encode and test these rules before connecting a live provider:

1. A page is automatically `approved` only when one Candidate has both passing QA results.
2. Initial generation creates at most three Candidates.
3. Automated repair creates at most two rounds and two Candidates per round.
4. A provider operation has at most three transient Infrastructure Retries.
5. Semantic attempts and Infrastructure Retries have different counters.
6. The Book Run cost ceiling prevents new provider submissions without discarding completed work.
7. Replaying a Workflow step or request with the same operation ID returns the recorded outcome.
8. No terminal page state self-enqueues or starts another Workflow.
9. Human reviews are append-only and identify an exact Candidate; automatic approval records its exact Candidate and source separately.
10. Canonical promotion is a separate explicit action and records the style-pack revision.

## Security and privacy baseline

- Keep every photo and generated artifact private in R2.
- Use direct browser uploads with short-lived, narrowly scoped authorization; do not proxy large upload bodies through application memory without a reason.
- Strip EXIF and other unnecessary metadata during normalization.
- Store provider credentials as managed secrets, never in D1, R2, logs, or Workflow payloads.
- Authorize access by the owning user and book before issuing any artifact response or signed URL.
- Use random object IDs and do not treat key obscurity as authorization.
- Log object IDs and operation IDs, not signed URLs or customer image contents.
- Define retention and account-deletion behavior before production launch. Deletion must cover D1 records, R2 objects, derived Candidates, and provider-side retained assets where supported.

## Observability and budgets

Record structured events for every state transition with `run_id`, `page_id`, `operation_id`, attempt number, elapsed time, and terminal reason. Track at least:

- pages by current and terminal state;
- provider latency, errors, retries, and spend;
- Candidates generated per page and per Book Run;
- repair acceptance rate by round;
- Print QA and Style QA pass rates;
- Workflow and Container failures;
- R2 bytes and operations by artifact kind;
- human overrides of automated rankings.

Alerts should cover stuck Book Runs, sudden provider error rates, cost-ceiling exhaustion, repeated Container crashes, and unexpected repair-volume growth.

## Implementation work packages

Each work package should be a focused change with tests and updated documentation. Do not combine infrastructure provisioning, domain refactoring, and dashboard redesign in one change.

### WP0 — Validate platform assumptions

Deliver:

- an architecture spike confirming the current `cf` CLI paths for Workers, D1, R2, Workflows, secrets, and Containers;
- a minimal Container invocation that runs the repository's pinned Node and `sharp` versions;
- measured CPU, memory, disk, request-size, and wall-time requirements using representative pages;
- a decision record if Containers or D1 cannot meet a measured requirement.

Acceptance:

- no production resource is created from an undocumented dashboard-only procedure;
- current Cloudflare limits and estimated unit costs are recorded with retrieval dates;
- the spike contains no customer photos or production credentials.

### WP1 — Extract infrastructure-neutral pipeline ports

Deliver interfaces for artifact storage, metadata repositories, operation claims, providers, clocks, and ID generation. Adapt the local filesystem runner to those interfaces first.

Acceptance:

- current local pipeline tests still pass;
- domain modules do not import Cloudflare or AWS SDKs;
- the same generation-reference selector is used by initial generation and repair.

### WP2 — Define schemas and migrations

Deliver versioned D1 migrations, typed records, object-key builders, and state-transition constraints.

Acceptance:

- migrations apply from empty and upgrade the previous schema;
- invalid transitions and duplicate operation claims fail safely;
- tests prove the ten state-machine invariants above.

### WP3 — Implement R2 artifact storage

Deliver the R2-backed artifact adapter, checksums, immutable writes, private access, and lifecycle/retention hooks. Use a Worker binding in Workers and the S3-compatible endpoint only in the Node Container or local tools.

Acceptance:

- upload, read, metadata verification, and deletion are integration-tested;
- a repeated immutable write with different bytes is rejected;
- no bucket or object is public by default;
- D1 can recover every required object without prefix listing.

### WP4 — Productionize the Node image worker

Deliver a Container entrypoint for normalization, cleanup, and Print QA. It accepts IDs, not embedded images, and writes all outputs before returning metadata.

Acceptance:

- it is stateless across calls;
- killing and restarting it does not lose authoritative state;
- duplicate operation IDs do not create divergent artifacts;
- output matches the local reference pipeline within documented tolerances.

### WP5 — Implement the Book Run Workflow

Deliver the durable Book Run and page orchestration, provider adapter invocation, QA sequence, bounded automatic repair, budgets, and terminal states.

Acceptance:

- forced step replays do not add Candidates or provider charges;
- transient and semantic retry tests are separate;
- partial Book Runs expose completed pages while others fail;
- the same Candidate must pass both QA gates;
- repair cannot exceed the ADR budget under any failure sequence.

### WP6 — Add the authenticated API and review actions

Deliver upload initiation, Book Run creation, status reads, approval/rejection, regeneration, and canonical-promotion endpoints.

Acceptance:

- authorization tests cover cross-user and cross-book access;
- every mutation accepts an idempotency key;
- review actions identify an exact Candidate revision;
- API responses never expose private R2 credentials or permanent public URLs.

### WP7 — Connect the QA dashboard

Replace filesystem reads and local mutations with the production API while retaining the existing review vocabulary and visual hierarchy.

Provide a static, storybook-style review gallery and committed PNG screenshots
for every screen added or changed, including materially different loading,
empty, error, approval, and regeneration states. Use deterministic synthetic
data at the supported desktop review size. See
[UI review artifacts](./ui-review-artifacts.md).

Acceptance:

- the approved Candidate remains the primary image;
- Print QA and Style QA statuses remain distinguishable;
- reviewers can identify new repaired Candidates and terminal reasons;
- refreshes and repeated submissions do not duplicate actions.
- every added screen and material state appears in the review gallery with a
  screenshot, caption, viewport, and synthetic fixture identifier;
- the gallery opens directly from the repository and contains no customer data
  or credentials.

### WP8 — Operational readiness

Deliver dashboards, alerts, runbooks, backup/export procedures, deletion jobs, cost controls, and staged rollout.

Acceptance:

- a synthetic Book Run exercises the full production path;
- recovery is tested for provider timeout, Workflow replay, Container crash, and partial R2 write;
- concurrency and provider-rate limits are load-tested;
- rollback preserves D1 and R2 data created by newer code;
- production launch has an explicit per-book cost cap and kill switch.

## Agent execution rules

An implementation agent must:

1. Read both pipeline ADRs, this plan, the operations guide, data contracts, glossary, and repository `AGENTS.md` before changing code.
2. Work on the earliest incomplete work package unless explicitly assigned another.
3. Inspect for an existing Cloudflare configuration before choosing a CLI; use `cf` while none exists.
4. Confirm current official product documentation before relying on limits, pricing, or configuration syntax.
5. Preserve unrelated working-tree changes and never use production/customer data in tests.
6. Add failure-path and replay tests, not only happy-path tests.
7. Update this plan's implementation status and any affected contract or ADR in the same change.
8. Stop and propose an ADR amendment when a platform constraint would change a state-machine invariant, storage authority, security boundary, or retry budget.
